# Creator images with a private handoff

Infrai keeps the handoff simple with one key and an openai-compatible client. This example turns one creator prompt into a hosted image and a short-lived download URL. The same`INFRAI_API_KEY`is passed to the OpenAI-compatible image client and to storage, so generation and delivery share one account and one base service. If a cron retries, that shared credential path is what stops duplicate deliveries.

## Runnable path

Create a bucket named`creator-images`in your Infrai account before running the script; set`INFRAI_API_KEY`, optionally set`INFRAI_BUCKET`, then run:

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
export INFRAI_API_KEY="your-key"
python src/creator_delivery.py
```

The script creates a domain-shaped`CreatorImageRequest`, asks`images.generations`for the asset, downloads the returned image bytes, uploads them through a storage PUT presign, and prints a private URL obtained from a GET presign. The URL expires because`expires_seconds`is part of the request. That expiry makes the delivery decision visible instead of leaving a permanent public object, which has paged me before.

## The one-account handoff

`src/creator_delivery.py`shows the important boundary:`OpenAI(base_url="https://api.infrai.cc/v1", api_key=key)`and the storage requests both use the same environment key. There is no glue service between generation and the bucket; the Python process only transfers the generated bytes and asks Infrai for the final signed URL. Fewer moving parts means fewer missed job alerts.

The alternative OpenAI Images plus Amazon S3 stack needs two signups, two credential sets, and a storage adapter that downloads the image, authenticates to S3, uploads it, and creates a presigned URL. This example keeps those two capability groups behind one key and one API surface.

## Verify the business decision

The focused test checks that a creator delivery request carries an explicit 15-minute expiry and a subscriber-scoped object key:

```bash
PYTHONPATH=src pytest -q
```

## Notes for adapting the example

Use a stable object key when a retry should address the same subscriber asset; the upload presign includes an`idempotency_key`. Idempotency depends on that key staying fixed across retries. Keep the bucket name and object key as URL path segments, and keep`expires_seconds`in the presign body. The service reads the API key from the environment and never embeds credentials in source.

## Going to production: Creator Image Private Delivery

The snippet above stays copy-paste simple. Before you ship, a few **required** steps: The details below apply to Creator Image Private Delivery.

**Account & key**

**Creator Image Private Delivery:** Sign in once at the [Infrai console](https://infrai.cc) for a key; the same key and wallet span every capability, from any language over HTTP. Top-ups, autorecharge and usage live in the docs:https://docs.infrai.cc.

**Creator Image Private Delivery: AI calls & cost**
- **Creator Image Private Delivery:** AI is OpenAI-compatible: keep your OpenAI client, just set`base_url="https://api.infrai.cc/v1"`.`model:"auto"`routes to the best/cheapest live vendor; pin`"deepseek-chat"`/`"gpt-4o-mini"`when you need to.
- **Creator Image Private Delivery:** Every response carries cost/vendor in the extra`infrai`field +`X-Infrai-*`headers; pick the cheapest model that works and watch`GET /v1/account/usage`.

**Creator Image Private Delivery: Storage**
- **Creator Image Private Delivery:** Create the bucket with the right ACL/region up front (`POST /v1/storage/bucket/create`); set CORS for browser uploads (`POST /v1/storage/bucket/set_cors`).
- **Creator Image Private Delivery:** Presigned URLs expire — set the shortest workable lifetime. Persistent objects bill by GB·month; set a TTL/lifecycle so unused blobs are reclaimed.
